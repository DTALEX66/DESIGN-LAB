三、最值得你投入的六个方向

1. Beacon：最接近你缺少的“原生执行证据互通层”

为什么它对 WORK-LAB 有价值

你要保留 Codex、Hermes、DSH 各自的原生执行能力，就需要回答：

到底是谁执行了任务、执行到哪一步、发生了什么错误、结果经过什么验证？

Beacon 的方向确实匹配这部分需求。其当前覆盖表包括 Codex、Hermes 和 DeepSeek Harness；但表中也明确存在差异，例如 Hermes 的 Token 列未标支持，DSH 的 Approval 列未标支持。不能接上一个采集器，就假定所有执行器都获得同等完整的数据。

我的建议是把它放在下面这个位置：



原生 Codex / Hermes / DSH
          ↓
可选的 Beacon 采集适配
          ↓
脱敏、字段白名单、事件标准化
          ↓
WORK-LAB 现有 Telemetry / Receipt
          ↓
Observer 只读展示

不要把 Beacon 的数据库再提升成“第四个真相源”。

接入时最容易踩的坑

Beacon 的交互安装会预选 Managed 云端选项；仅登录不会转发，但确认 Managed 后会连接端点。它也具备采集提示词、回答等完整会话内容的能力，因此“Local-first”不能被理解为“任何默认安装方式都只留本机”。

而 WORK-LAB 当前禁止把提示词正文、回答正文和敏感凭据写入证据，并把部分 Hermes hooks、MCP 和模型配置字段划为只观察、不直接覆盖。所以这不是一个可以直接全局安装、自动修改 hooks 的任务。

建议第一轮只验证最小字段：



任务标识、执行器、运行标识、代码版本
开始/结束状态、命令结果、审批引用
产物引用、验证结果、耗时
可获得的用量数据及其来源

拿不到的字段显示 UNKNOWN，不要显示为 0，也不要用其他执行器的数据推算补齐。

**特别针对你之前的“网页 GPT → 原生执行器”需求：**Beacon 虽然列出了 ChatGPT 浏览器会话采集，但这仍然是观测能力，不能据此认定它能主动调用网页 GPT、提交任务、管理额度或完成闭环调度。

结论：优先试接，但定位为受控采集插件，而不是新的调度中心和知识中心。

2. SoL-Pi：你应该拿走的是“减少无效消耗的办法”

先纠正“最高节省 64% Token”

官方结果中，相对 Pi 的 Token 降幅是 45%–49%；相对模型原生 Harness 的降幅是 35%–64%。同时，组合方案保留了约 94% 的 Pi 平均得分。另一个 63 题测试里，Codex、Pi 各完成 18 题，SoL-Pi 完成 15 题。这不是“所有任务能力不变、稳定省 64%”的证据。

对你最有价值的具体机制

SoL-Pi 公开的核心机制包括：大结果按句柄回读、保留证据的日志缩减、编辑与后续验证合并，以及在合适的子任务边界压缩上下文。它们运行在 Pi 的扩展环境中，不能原样当成 Codex 或 Hermes 插件安装。

我建议按下面的方式借鉴：

机制你的使用场景必须保留的约束





大结果引用与精确回读

全量审计、长测试日志、重复读取大型源码

原始内容可定位；代码改动后不能继续引用过期快照

日志证据缩减

把上千行失败日志变成可定位的问题摘要

失败、超时、跳过不能被压掉；摘要必须能回到原始证据

确定性动作合并

修改之后执行已批准的对应验证

不得借“合并工具”跳过中间必须发生的审批

阶段性上下文整理

长任务从调研切换到实现、从实现切换到审查

保留未解决问题、约束、版本和真实完成状态

这里还有一个容易被忽略的区别：

引用的日志行真实存在，只能证明“这句话出现过”，不能自动证明 Agent 对错误原因的解释正确。

所以，日志缩减可以帮助定位问题，但不能替代测试复现和独立审查。

对你而言，我会先试 “大结果回读 + 日志证据缩减”，再考虑更深入的上下文干预。它们更容易以局部能力接入，不必迫使你换掉原生执行器。

3. Prompts.chat + OpenAI Skills 方法：把“提示词库”变成真正能执行的能力

Prompts.chat 提供 MCP 接入，提示词数据采用 CC0，网站代码等部分采用 MIT。它适合作为外部模板来源，但社区提示词本身不是经过你项目验证的 Skill。

我建议这样使用：



检索外部提示词
    ↓
AAOS 候选资料
    ↓
检查来源、适用范围、冲突与风险
    ↓
改造成项目模板
    ↓
用真实任务验证
    ↓
经审核后成为版本化 Skill / Method

例如，一条“品牌总监提示词”不能直接成为 DESIGN-LAB 的专业能力。它还需要补齐：

输入资料要求、输出物、尺寸和格式约束、风格一致性标准、可编辑交付要求，以及失败时该如何处理。

你的 AAOS 已有 ingest_candidate()、research_github_repository() 和候选包读取入口。应该复用这一条候选治理链，而不是为了提示词再部署一个平行的知识系统。

OpenAI 那篇文章，最值得采用的是“精确加载”

官方文章确实强调更准确的 Skill 触发、更少的无关指令以及明确的任务完成条件。

落到你的三个项目，我建议采用：



全局规则：只放跨项目长期有效的底线
项目规则：只放本项目职责、路径和验收条件
专项 Skill：任务需要时才加载
参考资料：按需查阅，不整包塞入上下文

规则精简不是削弱规则。

应该删除的是重复要求、过期路径和无条件触发；应该保留的是授权边界、单写者约束、原生模型选择、真实验证和发布审批。

4. GEP / EvoMap：最适合 AAOS 的是“有适用边界的经验”，不是自动自我进化

当前 SDK 与你的描述有一个重要区别

当前 GEP SDK 明确说明：它不携带进化算法代码。主要提供 Gene、Capsule、EvolutionEvent 等结构、协议常量、内容哈希和验证辅助函数。算法行为在其他实现中。其许可也有版本差异：1.3.0 及之后的代码采用 Apache-2.0，较早版本曾采用 GPL-3.0；规范文档另有 CC-BY-4.0 许可。

因此，不能把：



装上 GEP SDK

直接理解成：



三个项目获得持续自我进化能力

你真正值得吸收的结构

我建议把可复用经验设计成：



什么问题
在什么环境和版本下发生
采用了什么方法
有哪些禁止条件
通过什么验证
对应哪些产物和来源
在哪些情况不再适用
由谁审核，何时失效

举例：

“某个 UI 导出流程在指定宿主版本中成功，产物经过字体、尺寸和可编辑性验证。”

这比：

“AI 学会了高质量 UI 设计。”

更适合你的 AAOS，也更容易被 DESIGN-LAB 安全复用。

具体做法应该是“字段映射”，不是用 Gene/Capsule 替换 AAOS 的整个对象模型。 内容哈希能证明对象内容是否一致，不能证明经验正确、来源可靠或可以自动执行。

AutoResearch 与 Dream-RSI 怎么处理

AutoResearch 更适合受控的研究实验，例如比较检索策略、资料切分方法或某类处理流程；它的价值在于实验组织和证据，而不是允许 Agent 不断修改生产系统。仓库示例还出现了跳过权限的运行方式，不能照搬到你的活动仓库。

Dream-RSI 则应继续作为研究参考：官方公开仓库已经存在，但当前仍说明代码准备发布，尚不能作为成熟可安装框架接入。

结论：先把“经验可追溯、可审核、可失效”做扎实，再讨论经验驱动优化。不要把产品中的“RSI”字样当成效果保证。

5. ChatCut：这份清单里最直接对应 DESIGN-LAB 视频生产的项目

它不只是“Claude Code 衍生应用”

官方公开的 ChatCut-Inc/agent-plugin 支持 Codex、Claude Code 等宿主，能够操作 ChatCut 项目，包括导入素材、修改时间线、字幕、动效、导出以及检查编辑是否反映到编辑器中。它需要 ChatCut 账号和项目权限，并通过托管 MCP 服务连接。公开插件仓库不等于整个剪辑器和服务端全部开源。

这与你的原生软件路线很匹配：



DESIGN-LAB 提供：
设计方法、脚本结构、品牌规范、字幕与动效标准、交付检查

Codex 等原生 Agent 负责：
按原生能力理解与执行任务

ChatCut 负责：
真实视频项目、时间线编辑与导出

不需要你重新开发视频编辑器。

应该怎样验证，才算真的接上

我建议选一个很小的真实视频任务，要求同时完成：

素材导入 → 时间线修改 → 字幕或动效 → 编辑器回读 → 重新打开项目 → 导出文件检查。

验收不能只看“Agent 说完成”或一张预览图，还要检查素材缺失、字幕时间轴、画面比例、音画同步、项目可继续编辑，以及最终交付文件是否真的存在。

同时保留账号费用、素材上传范围和素材使用权的检查。不要默认它是纯本地工具，也不要默认它支持所有其他剪辑软件的工程格式互转。

**优先级要看你的当前业务：**继续以文化墙、VI、UI 和静态视觉交付为主时，它是视频扩展项；启动短视频生产时，它可以直接升为第一批验证对象。

6. OpenMausBot：比“普通多模型聊天壳”更值得看，但要控制引入成本

这里需要给它一个比你清单简介更准确的评价：

OpenMausBot 不只是调用模型 API；它也可以利用已安装、已登录的原生 CLI。 这一点比重新封装一个通用模型网关，更接近你希望保留原生执行能力的方向。

值得观察的是它如何处理不同执行引擎、会话身份、权限提示和任务状态，而不是单纯看“多个联系人聊天”这个界面。

不过当前 README 也明确说明，API Key 会以明文保存在私有配置文件；核心开源部分与 enterprise/ 的许可证不同，打包的桌面控制组件还有各自的上游许可。

因此，我的建议是：

先把它作为独立软件，用一个不含敏感资料的原生 CLI 任务验证价值。

只有它确实减少了你在原生软件之间切换、交接和追踪任务的成本，才值得写适配器。否则它只是增加一个还要维护的入口。

“每个 Agent 一个联系人”也不能被当作权限隔离证明。真正要验证的是不同 Agent 是否能越权读写彼此目录、使用未授权工具或共享凭据。

四、你列的“公共组件四件套”，需要重新定义

你最上面的这组组合：

Oh-My-Hermes 调度 + Jev 评分 + Beacon 日志 + MCP 工具

可以作为候选能力分类，但不能直接当成已经成立的三项目公共架构。

Oh-My-Hermes：只在 Hermes 范围内选用

至少存在 rlaope/oh-my-hermes 与 witt3rd/oh-my-hermes 两套不同实现。前者包含大量专项技能、模型工作流和长期记忆；后者侧重原生 Hermes 多 Agent 技能与验证循环，而且部分隔离能力在缺少原生工具范围限制时仍依赖提示词约定。

我的建议是选取一个具体版本中的少量流程，例如“独立审查”或“研究—验证循环”，让它只增强 Hermes。

不要让它再管理 Codex、DSH 的模型选择，也不要将其长期记忆提升到 AAOS 之上。

Jev：有评分用途，但不能成为总裁判

目前可核验的 Jev 是结构化评估模型路线，提供 Choice、Score 等输出。相关 LangChain 实验使用的是一个很窄的固定天气回答样本集，不能外推成“所有代码、知识和设计任务都能可靠打分”。

合理的位置是：



确定性检查
    ↓
Jev 等辅助评分
    ↓
出现矛盾、证据不足或高风险问题
    ↓
更深入的复核 / 人工审批

测试是否通过、文件是否可编辑、实际尺寸是否正确，都不应被一个模型分数覆盖。也不能在没有核验输入能力的情况下，假定它能承担专业视觉评审。

Beacon：采集候选，不是新知识权威

采集之后，哪些数据允许进入 WORK-LAB、哪些经验允许进入 AAOS，应继续由你的现有边界决定，不能由采集器自行扩大范围。

MCP：是接入协议，不是总调度机制

MCP 定义工具与资源接入方式，但并不替你完成跨执行器任务所有权、持久状态、审批与最终验收。

同样，支持 MCP 不代表能自动桥接网页 ChatGPT 的交互与额度。

五、暂不进入核心的项目，具体卡在哪里

cc-haha：来源风险没有解决前，不做代码吸收

仓库历史讨论明确出现基于泄露版本代码开发的说明。这个事实足以让它进入来源审查名单，但本次没有逐文件追溯当前全部代码，因此也不应把历史情况无限外推成对所有现行文件的结论。

稳妥做法是研究它的团队视图、差异审阅和审批交互，独立实现需要的界面。仓库挂着 MIT 标签，不足以替代完整来源核验；“仅供学习”也不能自动消除来源问题。

EigenFlux：现在会增加外部信任面，而不是解决你的内部重复

它面向跨 Agent 的信息发布、发现和交流。

但你的三个项目属于同一套受控工作体系。建议先用本地任务引用、证据包和知识查询接口联通。未来确实需要外部 Agent 经验发现时，再以只读、脱敏、候选隔离方式接入。

不要让外部网络返回的“经验”直接触发本机执行，更不要广播你的私有源码、任务轨迹或客户资料。

AMD Token Factory：费用线索值得保留，宣传条件不能先写死

本次找到的官方 Radeon/Token Factory 入口，尚不足以核实你列出的 DeepSeek V4、Qwen3.8、国内直连、无需绑卡和每日动态额度全部条件。

在实际账号验证前，应该标记为：



状态：待验证
模型目录：未知或待回读
工具调用能力：待测试
额度与限流：待确认
生产可用性：不作保证

它只能成为可选 Provider，不应该让 WORK-LAB 自动改掉你原生客户端已有的模型选择。

安全工具与 VibeCoding 案例：保持用途独立

Dalfox、Nuclei 可以服务于有授权的测试环境，但你给出的地址不足以还原短视频中的完整漏洞赏金 Agent 流水线。

电动车案例则适合作为产品拆解资料。另一个小问题是，你写的“VibeCoding 五件套”实际只列了四项；没有必要为了凑出第五项而新增依赖。
