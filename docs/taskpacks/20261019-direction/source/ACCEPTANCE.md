# DESIGN-LAB 验收与交付清单

## 必交付
1. 基线记录：仓库、分支、HEAD、dirty 状态、Authority/索引/任务账本位置。
2. 定位冲突矩阵：旧表述、冲突原因、处理结论、影响文件。
3. 更新后的正式 Authority 与产品边界，附差异摘要和历史替代关系。
4. 能力映射表：六大能力域 → 现有模块/Schema/Registry/Adapter → 现有证据 → 缺口 → 后续任务。
5. 技术可行性矩阵：本地/云端模型、视觉分析、提示词反推、API/MCP/插件/脚本/UI 自动化、读回/恢复、AAOS 候选接收。
6. 任务重排建议：复用既有账本与 W00—W17 等编号，不另建平行总账。
7. 测试/验证报告：命令、退出码、测试摘要、精确 SHA、未执行项与原因。
8. 修改文件清单、风险、回滚方法和下一步建议。

## 验收标准
- [ ] 定位明确为专业视觉智能与可复用设计能力系统。
- [ ] 明确排除第二画布、通用编辑器和全流程设计文件交付平台。
- [ ] 六大能力域均有明确输入、输出、边界和验证方式。
- [ ] 本地/云端/混合模型为可替换策略，不将推测能力当成已验证能力。
- [ ] API/MCP/插件/脚本/UI 自动化有分层策略与真实任务验证要求。
- [ ] WORK-LAB 的通用治理与 DESIGN-LAB 的专业视觉能力边界明确。
- [ ] AAOS 知识回流采用候选/审核/接收流程，不直接写入可信知识。
- [ ] 既有有效实现、历史证据和用户未提交更改得到保护。
- [ ] 不存在虚构完成状态、虚构测试或未证实的“已接入”声明。

## 最终报告格式
1. 结论：PASS / PARTIAL / FAIL / BLOCKED。
2. 基线：分支、HEAD、工作树状态。
3. 修改文件及每项修改理由。
4. 冲突矩阵与权威优先级。
5. 六大能力域的实现映射与缺口。
6. 技术可行性和风险。
7. 测试命令、退出码、证据位置。
8. 未完成事项、阻塞原因和建议下一步。
9. 回滚方式。
10. 明确声明：文档修订、规划完成、代码实现、真实运行、人工验收、AAOS 接收是不同状态，不得混为一谈。
