## 1. 交付

`/projects/:id` 的参考素材面板新增**批量导入**：

- 多选文件（`multiple`，仅 PNG/JPEG）
- 逐个 POST（服务端一次请求只接受一个 `content_base64`）
- **逐文件结果**：已导入 / 失败（附各自原因）/ 已取消
- **汇总只数真实结果**：`导入 N 个：成功 x · 失败 y · 已取消 z`，并注明失败项未写入
- 批次结束后**从服务端重新读回清单**，并在读回期间明确标注「正在从服务端重新读回清单…」

## 2. 取消语义（写明，不靠暗示）

| 事项 | 语义 |
|---|---|
| 生效时机 | **下一个文件开始前**生效 |
| 正在上传的那个 | **让它完成**，并按其**真实结果**记入 |
| 是否中途 abort | **不**。已发出的写入可能在服务端已落盘；声称「已取消」等于把**未知结果报成已知**——正是待审面板要避免的错误 |

页面在选择取消后即显示：「已请求取消：正在上传的这个文件会完成，其余不再开始。」

## 3. 验收对照

| 包内 W04 验收 | 做法 | 结果 |
|---|---|---|
| **批量导入可取消** | 在**真有文件在传**时点取消（第一个 POST 被刻意延迟 1800ms） | ✅ |
| **报告部分失败** | 3 个文件：1 个类型不合格（客户端拦截）+ 1 个 POST 被 abort（服务端路径）+ 1 个成功 | ✅ |
| 失败项不得计入导入 | 断言恰有 1 行是「已导入」 | ✅ |
| 每项失败给出自身原因 | 「不支持的媒体类型 text/plain：仅 PNG / JPEG」/「Failed to fetch」 | ✅ |
| 可取消且不静默丢弃 | 断言 3 行齐全、其中 2 行为「已取消」 | ✅ |
| 取消后仍反映真实状态 | 读回数量 = 阶段 A 的 1 + 阶段 B 实际导入数 | ✅ |

`11/11` 通过。

## 4. harness 抓到的**我自己代码里**的一个真实缺陷

第一版在取消路径上 `continue` 之后**没有重新渲染**，而且成功提示被 `!cancelRequested` 挡掉。后果：

> 取消一个批次后，界面上留着的**是上一批次的结果与汇总**——用户会把**别人的结果读成这一次的结果**。

这与本轮一直在防的「把不知道的报成知道的」是同一类错误，只不过发生在 UI 状态里。已修：循环结束后**无条件**渲染最终行，并给出取消专属的结论文案。

## 5. harness 自身的两个竞态（同一根因：等待了**上一阶段就已满足**的条件）

| 错误 | 假结果 | 修法 |
|---|---|---|
| 阶段 B 等 `/导入 3 个：/` | 该文案**阶段 A 就已存在** → 等待立刻返回 → 读到的是**阶段 A 的行**，于是「取消」看起来完全没生效 | 改为等**阶段 B 专属**文案 `已取消 2`，并等 c3.png 出现在结果里 |
| 阶段 A 读标题早于异步读回 | 标题仍是导入前的 `参考素材（0）`，与「已导入」自相矛盾 → 误判读回失败 | 产品侧在读回期间显示「正在从服务端重新读回清单…」，harness 等待该标记**消失**后再读 |

第二项不只是修 harness：**产品侧也因此更诚实**——「循环跑完」与「清单已反映服务端」不再可能被混淆。

## 7. 未覆盖 / 边界

- 仍**不**提供「中途 abort 已发出请求」的能力（理由见 §2）。
- 客户端闸门与旧导入完全一致（PNG/JPEG、单个 ≤ 32 MiB）；未新增格式。
- 导入**不做**去重提示：同一文件重复导入会各自成为一次导入（服务端以 id 幂等键区分，每次新键即新资产）。
- 权利仍为 `NOT_REVIEWED`（服务端写入值），面板只呈现。
- 证据等级：**E2 CONTROLLED_RUNTIME**。
