# W14 step 1 —— 运行时采样基线（包内要求「先采样现状」）

**状态：** W14 的第一步完成。**这不是 W14 完成**——状态矩阵、中文 IME、键盘/焦点/菜单/拖放、
离线/任务中断/字体缺失、axe、wheel 安装态、滚动流畅度、千资产索引**本轮均未做**。
**证据：** `evidence/W14-RUNTIME-SAMPLING.json`（机读原始数据）
**harness：** `harness/w14-runtime-sampling.py`（Python 起真实服务）+ `harness/w14-sampling.mjs`（浏览器测量）
**性质：** 只读测量。**未修改任何产品文件。**

## 1. 方法

沿用仓库既有 E2E 的可靠方向：**Python 起真实 loopback 服务**（`ProjectService` + `make_server`，
真实 CSP、真实 `/api`），再以子进程拉起固定版本 Chromium 采样。
在临时合成项目上连接令牌 → 逐路由切换 → 记录时间。

## 2. 结果（E2 CONTROLLED_RUNTIME）

| 指标 | 实测 | 包内拟定目标 | 结论 |
|---|---|---|---|
| 本地首屏可交互 | **71 ms** | ≤ 2000 ms | 通过（约 28× 余量） |
| 热路由交互 P50 | **12.5 ms** | — | — |
| 热路由交互 **P95** | **19.8 ms** | ≤ 200 ms | **通过（约 10× 余量）** |
| 热路由最大 | 22 ms | — | — |
| 控制台错误 / 页面异常 | 0 / 0 | 0 | 通过 |

12 条路由各 5 个样本，全部 `obs=5/5, to=0, valid=True`。

`workbench` 路由**不计入**渲染延迟：它不渲染进 `#route-view`（`show()` 对它是特例，只切换
遗留 `#workspace`/`#login` 区域后 return）。实测其切换为 29 ms（P95），已在机读数据里单独标注
`kind=visibility-toggle`，而不是让它污染聚合值。

### 2.1 缩放矩阵（1920×1080 / 2560×1440 × 100/125/150/200%）

**正确做法**：Windows 缩放缩小的是 **CSS 视口**，不改 CSS 布局。所以按「物理屏 ÷ 缩放」得到
CSS 视口（2560×1440 @150% → 1707×960；1920×1080 @200% → 960×540）。

16 个单元格（2 屏 × 4 缩放 × 2 路由）全部 `app_visible=true`：

| 检查 | 结果 |
|---|---|
| 文档横向溢出 | **0 / 16** |
| `.content` 被裁出视口 | **0 / 16** |
| 越界元素（排除被 `overflow-x` 裁剪者与关闭态浮层/装饰） | **0 / 16** |

**检测器已正控**：注入一个 `position:fixed; left:100%; width:200px` 元素（其右边界 = vw+200），
同一个越界判定必须报出它 —— 实测 `baseline=0 → with_control=1, control_detected=true`。
没有这条正控，「0 问题」只是盲区。

## 3. 本轮 harness 自身的 4 个错误（每个都曾给出过假数字）

记录它们，因为它们证明了那些数字**不能**直接采信：

| # | 错误 | 产生的假结果 | 修法 |
|---|---|---|---|
| 1 | 点完只等 2 帧再读 `aria-busy` | 60 个样本里只有 1 个观察到 busy，11/12 路由落进「3 帧兜底」→ 全路由报 53–82 ms 且**异常整齐**。那是**测量地板**，不是渲染耗时 | 改用 `MutationObserver` 观测真实变更，并回报是否观察到异步阶段 |
| 2 | 每个路由连点 5 次同一项 | 同 hash 不触发 `hashchange` → 不重渲染 → 12 路由**全部**报 5009 ms（= 5 s 超时） | 轮转采样，并在必要时先切走再切回，保证真实跳转 |
| 3 | 有效性公式把 busy 与 loading 两个计数器相加 | 单个样本可同时满足两者，和会超过样本数 → **11 条有效路由被误判为无效** | 改为每样本一个布尔「观察到阶段」 |
| 4 | 正控注入进 `.app` 后测出 0×0 | 误以为「检测器看不见越界」。真因：连接后停在默认 `workbench` 路由，而该路由下 **`.app` 是 `display:none`** | 正控先切到 dashboard；并给每个矩阵单元格加 `app_display/app_visible`，隐藏 shell 的单元格不算测量 |

第 4 条同时暴露了一个更值得记住的陷阱：**在 `workbench` 路由上扫 `.app *` 永远得到「干净」**，
因为整棵 shell 是隐藏的。所以矩阵单元格必须自带 `app_visible` 断言。

## 4. 明确未覆盖（不要把这些算作已验收）

- **非** E3：合成临时项目、本机 loopback、无头固定 Chromium `149.0.7827.55`、单机单次。
  不代表真实用户硬件，也不代表打包后的 wheel 安装态。
- `first-contentful-paint` 取值为 `null`（无头环境无 paint timing），因此「首屏可交互」用的是
  本 harness 的定义（登录控件可见且可输入），**不是**标准 FCP/TTI 指标。
- 缩放矩阵只测了 2 条路由 × 16 单元格，**不是** 12 路由全矩阵。
- 包内 W14 其余项**未测**：全部状态矩阵、中文 IME、keyboard/focus/菜单/拖放、undo 范围、
  离线、任务中断、字体缺失、axe 严重问题、wheel 安装态加载真实资源、滚动流畅度、
  千资产索引不全量加载原图。
- 包内明示：这些性能目标是**项目拟定目标**，不是既有实测，也不是上游承诺。

## 5. 结论

按包内「先采样现状」的要求，**现状已采样且检测器已被正控**：本机上热路由交互 P95 为
**19.8 ms**、首屏可交互 **71 ms**，均大幅优于拟定目标；16 个缩放/分辨率单元格无横向溢出、
无越界、无内容被裁。

**但这只是基线，不是 W14 通过。** §4 列出的项仍是 W14 的未完成面。
